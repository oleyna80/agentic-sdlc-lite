Без дополнительных GO на каждый fixture action и без внешней публикации fixtures. |
| OD-5 | Принять conditional routine NOT_APPLICABLE и precedence §6.4–6.5 без обхода mandatory gates. Project definition/specification с Owner, Critic до Owner approval exact P; stage W/Critic/REWORK/local decisions/next-stage autonomously внутри P; Owner escalation/final merge и отдельные deployment/security/external boundaries по §6.9. |

Any material project-proposal revision receives a new P and independent Project Critic before Owner consideration. After READY, Owner accepts or rejects exact P separately without changing the reviewed blob. A material requested change repeats the affected project planning/Critic/Owner cycle. Within approved P, Orchestrator refines W and local engineering choices and runs Stage Critic/REWORK autonomously; Owner returns only through §6.9 escalation, not for each W/commit/push/test/handoff.

## 6. Минимальный технический подход

### 6.1. Routine delegation и significant Coder

Coder и mission используют classification из development, не вводя собственный классификатор. Routine mission содержит цель/обоснование низкого риска, согласованный scope, branch/base, разрешённые пути, relevant checks, actual permission limits, checkpoint route и STOP. Frozen WB/Critic reference для routine — NOT_APPLICABLE с причиной, если Owner не потребовал дополнительные gates. Direct Orchestrator routine path сохраняется.

Для нового significant: approved specification → committed project proposal P → project Critic READY → Owner approval exact P/freeze; затем Orchestrator автономно готовит committed stage W внутри P → stage Critic READY/conformance → frozen W без редактирования → bounded Coder → source candidate → same-SHA независимые Reviewer/Verifier → authorized delivery/CI/closeout → следующий WB. Отдельное Owner approval W не требуется; §6.9 определяет входные условия и escalation. Уже принятый frozen legacy task plan сохраняет исходный порядок/provenance, не переутверждается задним числом. Новые задачи не используют «legacy» как shortcut. Normative policy edit нельзя назвать routine ради обхода проверок. Если routine scope стал significant — остановить реализацию и вернуться к согласованию/планированию.

### 6.2. Durable checkpoint и восстановление

Каноническая матрица находится только в memory; development/root/templates/task README ссылаются на неё и не создают конкурирующую обязательность.

| Ситуация | Минимальный checkpoint |
| --- | --- |
| Короткая routine в одной непрерывной сессии, без передачи или параллельной работы | Полноценный task PR/issue с целью/scope, branch/base и exact candidate, изменениями, фактическими checks, N/A rationale, рисками и следующим шагом. Отдельный handoff-файл не обязателен. |
| Routine прервана до PR, длится через несколько сессий, blocked или передаётся другому агенту | Собственный `docs/changes/<task>/handoff.md` и recoverable Git checkpoint разрешённой безопасной работы; наличие будущего PR не заменяет checkpoint сейчас. |
| Significant либо параллельная работа | Собственный committed task handoff на каждой соответствующей ветке, ссылки на planning/evidence; общий context не заменяет task state. |

Checkpoint содержит задачу, classification/scope, branch/base/наблюдавшийся HEAD, выполненную и оставшуюся работу, exact evidence, blockers и next action. HEAD — наблюдавшийся source/checkpoint predecessor, а не невозможный self-referential SHA содержащего его commit. Последующий Git/PR факт указывается с наблюдаемой revision.

Durable означает доступный следующей сессии committed Git state и/или надлежащий существующий PR/issue для допустимого короткого случая. Chat, агентный cache, uncommitted файл и сообщение «сохранил» не считаются выполнением committed-checkpoint requirement. Не коммитить секреты или небезопасную работу ради checkpoint.

Уточнить только canonical memory procedure: файлы `/tmp` и иной temporary scratch, локальная агентная `MEMORY.md` и compacted history — вспомогательные источники для поиска/реконструкции, не authoritative project state. Сверять их с applicable instructions, Owner scope, текущими Git facts и допустимым task checkpoint; не выводить из них approval, durable status или наличие временного пути. Остальные документы ссылаются на этот протокол, не дублируют его.

После context compaction или resume до следующей изменяющей операции повторно установить objective, applicable instructions, verified absolute worktree/expected branch/HEAD/status, approved scope, все dirty/untracked files, доступный task checkpoint и exact next action. Проверить target по §6.6; не предполагать сохранение shell cwd, tool state или temporary paths. При отсутствии checkpoint реконструировать факты из разрешённых источников с явной неопределённостью, применяя уже заданную матрицу, без вымышленного recovery PASS. Для короткой routine это повторная проверка контекста, не новый mandatory WB/independent gate/отдельный handoff.

Если commit/publication не разрешены, сохранить безопасное локальное состояние без удаления чужой работы, сообщить `NOT_COMMITTED` и конкретный недостающий checkpoint/authorization. Не заявлять recovery PASS/завершённую передачу и не выполнять скрытую публикацию. Внезапно оборванный процесс не может гарантировать checkpoint: следующая сессия проверяет actual Git/dirty state, реконструирует факты и явно обозначает потери/неопределённость. Протокол описывает обязательное действие при доступной возможности, а не runtime guarantee.

Parallel tasks не пишут «единственную активную задачу» в shared memory и не меняют одновременно project planning. Approved root plan не обновляется ради progress; один координатор сохраняет stage acceptance/next action в task handoffs/reports на согласованном checkpoint, сохраняя другие задачи. Material изменение plan — новый P по §6.9; новый manager/registry не вводится.

### 6.3. Ограниченный first-use guard

Изменить только Bash `run` существующего step `Guard new projects against inherited template state`. Использовать обычные Bash/grep/awk, без dependency installation, сети, service/runtime и общего Markdown validator.

1. Отсутствующий/пустой `GITHUB_REPOSITORY` — ошибка, не разрешение source exception.
2. Для любого repository требовать ровно одно поле `- **Repository identity:**` и полный exact line match ``- **Repository identity:** `<GITHUB_REPOSITORY>` `` в `PROJECT_BRIEF.md` (без завершающего пробела). Значение окружения сравнивается буквально, не как regexp/substring; дубликаты и противоречивые identity fields отвергаются.
3. Source exception доступен только exact `oleyna80/agentic-sdlc-lite`: его собственные source initialization/history/memory сохраняются. Prefix/suffix, fork или другой owner не получают exception.
4. Для derived repository требовать ровно одно поле `- **Initialization:**` с полным значением `INITIALIZED`. Остаточный SOURCE_REPOSITORY, отсутствие и дубликаты — ошибка.
5. Только для derived repository проверить конечный набор recognizers в `memory_bank/context.md` и `memory_bank/progress.md`, с привязкой к началу обычной Markdown bullet и точному ключу/значению-маркеру:

Marker fixtures брать из фактических строк этих файлов через `git -C "$task_worktree" show 90c101ba2b6091a24c2f458f5ffc8b02e6eb04ab:<path>` в явно выбранном repository с проверкой исходной revision; для этого read-only inspection полный write preflight §6.6 не требуется. Таблица ниже описывает группы, но не заменяет исходные строки: сохранять Markdown bold markers, backticks, punctuation и реальные value boundaries, включая закрывающее `:**` у датированного milestone label. Не реконструировать fixtures по упрощённому тексту таблицы.

| Файл | Запрещённый source marker в обычной активной записи |
| --- | --- |
| `memory_bank/context.md` | `- **Project:**` со значением в backticks `oleyna80/agentic-sdlc-lite` (включая последующее описание). |
| `memory_bank/context.md` | `- **Integrated baseline:** SDLC Lite v0.1 Foundation` с последующим описанием или концом строки. |
| `memory_bank/context.md` | `- **Delivered task:** WB-LITE-001` с последующим описанием или концом строки. |
| `memory_bank/progress.md` | Обычная датированная bullet с label `- **YYYY-MM-DD — WB-LITE-001 integrated into Foundation:**`. |
| `memory_bank/progress.md` | Обычная датированная bullet с label ``- **YYYY-MM-DD — Foundation v0.1 integrated into `main`:**``. |

Использовать границы значения/label, чтобы не ловить произвольный более длинный task ID или название. Конкретная дата не должна давать обход recognizer. Отсутствующие файлы отвергаются существующим canonical-documents step и standalone guard fixtures.

Не сканировать весь репозиторий на упоминания source owner/repo/PR/SHA. В проверяемых двух файлах prose/provenance bullets с другим ключом и blockquotes могут ссылаться на источник, не изображая собственный baseline. Исторические ADR, legacy plans и архивы не сканируются и не переписываются. Если source строка скопирована в обычной форме активной bullet, она распознаётся как marker даже при заявлении «это история»; допустимый provenance должен отличаться по форме. Guard не выполняет полный semantic Markdown parsing.

Вне автоматического покрытия: перефразированная source memory, все возможные чужие SHA/PR, смысл принятых ADR, reset decisions/log, платформенные настройки и весь first-use checklist. Они остаются предметом initialization review/fresh-session recovery. Не расширять список бесконтрольно и не называть проход guard полной initialization PASS.

### 6.4. Authority precedence

Сохранить root contract и его существующий порядок источников. Пояснить, что проектные документы применяются внутри реально действующей иерархии harness-инструкций, OS/platform permissions и security controls; документы/Owner task не отменяют технические ограничения. Это пояснение предела применимости, а не новый узел authority.

Approved task requirements уточняют цель, acceptance и ограниченный scope внутри root/procedures; ссылка на WB, роль, шаблон или отчёт не создаёт полномочий и не отменяет mandatory gates. Конфликт требует остановки затронутого решения и явного Owner disposition в допускаемых пределах. Сохранить существующее различие нормального gate result и отдельно обозначенного Owner risk exception: exception не превращать в READY/PASS и не расширять этим WB его действие.

### 6.5. Routine NOT_APPLICABLE и существующие статусы

В mission/handoff/closeout разрешить `NOT_APPLICABLE — <почему gate не требуется для этой routine>` для frozen WB/Critic и независимых Reviewer/Verifier, если Owner их не потребовал. Сохранить evidence focused checks/self-review; self-review не обозначать independent review. Owner-required routine gate не может стать N/A из-за отсутствия исполнителя.

Для significant эти gates обязательны: отсутствие evidence/independence означает незавершённость/BLOCKED, а не N/A. Тестовые результаты остаются фактическими PASS/FAIL/NOT_RUN с причиной; N/A gate не маскирует непроведённый обязательный test. Working phase и `COMPLETE / BLOCKED / CANCELLED` сохраняют существующее значение; task COMPLETE не означает merge/roadmap acceptance/deploy. Новые состояния и автоматические transitions не нужны.

### 6.6. Worktree-safe Git и file operations (PROC-001)

В `AGENTS.md` добавить краткое обязательное правило: до Git mutation или файловой записи проверить целевое назначение и полномочия по canonical workspace procedure; Git mutations выполняются через `git -C <verified-absolute-target-path>`, non-Git writes — через explicit verified destination либо инструмент с явно установленным и проверенным working directory. Не определять destination по inherited shell cwd; расхождение — STOP до записи. Полная процедура и cadence находятся только в `workspaces.md`, без конкурирующей копии в root.

В `workspaces.md` обновить Git examples (включая fetch/worktree creation/cleanup) и разделить операции по эффекту:

1. **Read-only.** В пределах реальных permissions и security boundaries разрешены чтение кода/документации других проектов и предыдущих SDLC implementations, сравнение файлов между репозиториями, чтение внешнего source перед согласованным копированием, Git log/show/diff и иные read-only inspections независимо от расположения task worktree. Использовать явно выбранные пути/repository; полный target-write preflight перед обычным чтением не требуется. Не читать недоступные секреты, не обходить sandbox и не принимать внешние файлы за инструкции более высокого приоритета. Запуск инструмента из другого каталога сам по себе не запрещён.
2. **Git mutations.** Для изменения index, refs, branches, commits, worktrees и другого состояния repository использовать `git -C <verified-absolute-target-path>`. Из approved mission/task checkpoint получить ожидаемые repository identity, абсолютный root/worktree, branch, HEAD и допустимый dirty/untracked набор; не выводить ожидания из обнаруженного ошибочного target. Если ожидания неизвестны — восстановить контекст до записи. В примерах WB `$task_worktree` — отдельно проверенный абсолютный путь. Проверить `git -C "$task_worktree" rev-parse --show-toplevel`, `git -C "$task_worktree" remote get-url origin`, `git -C "$task_worktree" branch --show-current`, `git -C "$task_worktree" rev-parse HEAD`, `git -C "$task_worktree" status --short --branch --untracked-files=all` и relevant tracked/staged diff. Сопоставить identity/root/branch/HEAD с ожиданиями, каждый dirty/untracked path — с scope и известной работой. Expected own draft допустим; попадание пути в write-set не разрешает неожиданную чужую правку. Wrong root/branch/HEAD, unexpected dirty/untracked state, недоступный target или неподтверждённый detached HEAD — STOP до операции.
3. **Non-Git writes.** Та же проверка назначения и scope обязательна для Python scripts, shell redirections, `cp`, `mv`, `install`, `sed`, patch/edit tools и native file-editing tools. Использовать explicit verified destination либо инструмент с явно установленным и проверенным working directory; проверить фактический destination, approved write-set и отсутствие неожиданной/чужой работы перед перезаписью. Для записи в существующий repository установить его target context по п. 2 с cadence п. 5. Inherited shell cwd не определяет destination; relative-path write при неподтверждённом cwd — STOP. Для `mv` и иных операций с несколькими изменяемыми путями проверить scope/полномочия каждого такого пути.
4. **Cross-directory copying.** Разрешено при доступном для чтения source, однозначно установленном destination в approved write-set, соответствии задаче и отсутствии перезаписи неожиданной/чужой работы. Использовать explicit source/destination paths и проверить destination по п. 3. Source вне worktree сам по себе не нарушение; write authority относится прежде всего к destination. Не превращать проверку destination в общий запрет внешнего чтения или согласованного копирования.
5. **Cadence и post-state.** Допустима серия связанных записей в неизменном подтверждённом контексте, approved scope и без признаков внешнего изменения; не повторять полный Git preflight перед каждой отдельной командой. Обновлять ожидаемые факты из наблюдаемого результата разрешённой операции и проверять соответствующий post-state. Повторный preflight обязателен при смене repository/worktree, branch/HEAD или существенном изменении состояния, после resume/compaction, при неожиданных файловых изменениях и перед переходом к commit, branch/ref manipulation, destructive operation или cleanup с проверкой отдельного полномочия. Это не заменяет sandbox, OS permissions и реальную isolation. `git -C` не изолирует shared refs/objects, не даёт полномочий и не устраняет concurrent-writer races; one-writer rule сохраняется.
6. **Repository bootstrap.** При создании/клонировании нового repository worktree ещё может отсутствовать. До операции проверить разрешённый parent/destination, отсутствие неожиданных файлов/коллизии, необходимое разрешение на создание и допустимое действие; не требовать несуществующий HEAD. После создания выполнить обычный repository/worktree preflight. Для добавления worktree существующего repository сначала проверить управляющий checkout/base и отдельно destination, затем новый target. Bootstrap exception не разрешает менять существующий repository без проверок; cleanup по-прежнему требует применимого отдельного разрешения.

### 6.7. Verification coverage (PROC-002)

В development закрепить: PASS относится только к явно перечисленному реально проверенному набору файлов/содержимому на указанном SHA или dirty snapshot. В workspaces дать команды/порядок: inventory tracked diff, staged diff и untracked paths через explicit target; обычный `git -C "$task_worktree" diff --check` не охватывает untracked files и не подтверждает всю candidate coverage.

До staging отдельно прочитать каждый разрешённый untracked file и проверить его содержимое: whitespace/conflict markers, Markdown links и relevant requirements. Для whitespace допустим comparison с пустым файлом или известным baseline через `git -C "$task_worktree" diff --no-index --check <baseline-or-empty-file> <absolute-file>`, либо явный content check. Записать paths, hashes, команду, diagnostics и exit code; код 1 может сопровождать существующие различия и сам по себе не означает whitespace failure или PASS. Проверить доступность inputs и сопоставить diagnostics/содержимое с ожидаемым поведением; error/неясный результат не превращать в PASS.

После staging, покрытого предоставленными полномочиями (без нового GO, если они уже достаточны), выполнить `git -C "$task_worktree" diff --cached --check` и просмотреть полный `git -C "$task_worktree" diff --cached`; сопоставить staged paths/content с проверенным набором и approved scope. Изменение файла после проверки требует affected повторной проверки; staging не разрешать только ради проверки. Это уточнение focused checks для любой classification, без нового mandatory gate для короткой routine и без нового test framework.

### 6.8. Progressive Git / native agent hooks — отдельный будущий scope

Owner задаёт принцип постепенного внедрения Git hooks и native agent hooks после предварительной проверки: documented operating rule → изолированный prototype подходящего hook → positive/negative tests и проверка реального harness/runtime → анализ false positives, overhead, permissions, bypass limitations и rollback → Owner approval включения в конкретном проекте → controlled rollout → возможное расширение enforcement только после успешных проверок.

В WB-LITE-002 реализуется документированное правило §6.6; prototype и дальнейшая hook automation требуют отдельного scope после проверки необходимости и доступных механизмов. Здесь не создаются, не изменяются, не устанавливаются и не активируются новые hooks; существующие `.githooks` сохраняются без изменений. Не добавлять обязательные hook-runtime, installer, wrapper, Controller или dispatcher и не ставить исполнение WB/routine workflow в зависимость от будущих hooks.

Git hooks не способны предотвратить произвольную файловую запись до вызова Git. Native hook events и поддержка различаются между Codex, Claude Code и другими harness: наличие конфигурации не доказывает реальное событие/исполнение или универсальную поддержку. Будущее enforcement оценивается по наблюдаемому runtime конкретного проекта, не по общему обещанию; сейчас hook prototype/runtime tests не входят в implementation fixtures и не выполняются.

### 6.9. Два уровня: project definition и autonomous stage execution

**A. Project definition — Owner participates.** Owner задаёт idea, цель и ожидаемый результат. Агенты помогают сформулировать specification/архитектуру; Owner разрешает существенные вопросы и утверждает итоговую specification. Architect/Orchestrator готовит complete project plan: scope/non-goals, constraints/risk posture, milestones/dependencies, outputs, проверяемые project/stage acceptance criteria, Git/delivery/autonomy bounds и escalation. Единственный root `plan.md` использует существующий template; это task-specific planning contract в текущей precedence, не второй AGENTS или новый authority layer. Новому standalone significant вне approved project plan достаточно compact single-stage project plan с теми же свойствами; routine project plan/WB не обязателен. Не требовать подробных WBs для всех будущих stages заранее.

При предоставленной planning commit authority Orchestrator фиксирует exact project candidate **P**. Independent Critic проверяет ещё не Owner-approved P: READY означает готовность к Owner review, не authorization; REWORK возвращает Orchestrator/Architect к новому P и повторному Critic без обязательного Owner на каждом цикле в пределах intent. Owner после READY принимает/отклоняет exact reviewed P. При принятии те же байты становятся frozen project contract; отдельные Owner decision/project Critic report ссылаются на P/path/blob. Approved plan задаёт delegated autonomy, но не создаёт OS/platform permissions. Material изменение требований Owner либо иной существенный plan change → новый P, affected Critic до нового Owner approval. Status/progress/approval/evidence не дописывать в approved plan.

**B. Stage execution — autonomous Orchestrator.** Внутри approved P Orchestrator делает actionable stage WB **W**: чёткое начало, entry conditions/dependencies и их evidence, bounded scope/write-set, expected artifacts, AC/checks/risks/rollback, permissions и STOP. Parent P/spec/constraints известны до W; conformance доказан ссылками и явным сопоставлением bounds. Orchestrator коммитит complete W в покрытых полномочиях, независимо запускает stage Critic на exact W. Stage REWORK → planning/new W/re-Critic автономно. Stage READY разрешает продолжить только внутри approved P/actual permissions: это assurance, не новые полномочия и не запрос Owner approval каждого W. После READY и подтверждения conformance Orchestrator использует тот же WB blob как frozen execution contract; verdict/conformance/phase отдельно.

Coder получает bounded mission → focused tests/source candidate **S** → independent Reviewer READY + Verifier PASS на одном exact S. REWORK/FAIL возвращает Coder автономно, corrected source — новый S и renewed affected assurance. Отсутствующий обязательный gate нельзя заменить self-review или N/A. Разрешённые source/evidence commits, non-force task push/PR, required CI на exact final HEAD **H** и durable closeout/handoff завершают stage только при его собственных acceptance/dependency/delivery criteria. Коммиты source для проверки могут предшествовать assurance, итоговый push/CI — после; ни один этап не доказывает следующий автоматически.

Когда completion подтверждён, Orchestrator без повторного Owner approval начинает следующий W: использует точные принятые outputs и source lineage, повторно проверяет его entry conditions/scope/permissions и stage Critic до Coder. Если GitHub CI обязателен, PENDING/NOT_RUN блокирует progression; если неприменим — обоснованный N/A, не вымышленный PASS. Plan может разрешать sequential descendant task/delivery branches; merge в `main` не требуется между WBs, если не включён в stage criteria. Если criteria требуют merge/внешнего действия с отдельным Owner GO, stage ждёт фактического authorization/evidence; не обходить gate и не объявлять completion. Frozen plan/WBs не править ради stage status; progress и next-action — task evidence. Task COMPLETE, stage acceptance, integration/merge/deployment остаются разными фактами.

**C. Local architecture decisions.** При технической проблеме Orchestrator привлекает Architect по необходимости. Architect анализирует варианты; если они сохраняют approved specification/P, constraints, risk posture и scope, Orchestrator выбирает подходящий, документирует rationale/alternatives и проводит affected checks без Owner approval. Локальная детализация не изменяет frozen W; если нужен новый контракт W в пределах P — новый W/stage Critic/conformance, без повторного Owner. Решение за bounds approved P/spec, material risk/scope/architecture-constraint change — Owner escalation, не скрытая local choice. Task evidence хранит rationale; durable ADR не создаётся побочным действием без своего scope.

**D. Escalation и final acceptance.** Owner вызывается при неразрешимом blocker/неоднозначности требований, material plan change, недоступном обязательном assurance или необходимом risk exception, выходе за preapproved permissions, и по завершении плана для финальной приёмки/merge decision. В project definition Owner также утверждает итоговую specification и exact Critic-reviewed P. Обычные stage planning/Critic/Reviewer/Verifier REWORK, локальные engineering choices, covered commits/push/tests/handoff и переходы далее дополнительных human approvals не требуют. Final merge невозможен без Owner GO после необходимой assurance/current-head CI; deployment/production/sensitive external actions/platform security changes сохраняют отдельное разрешение. Destructive cleanup и hook rollout — прежние отдельные scopes/permissions. Routine остаётся без обязательных WB/Critic/project plan, если Owner явно не требует их.

**Adoption boundary.** P, its independent Project Critic report and the separate Owner decision are immutable inputs named in §1. W and its separate conformance evidence link to approved exact P before Stage Critic; their subjects and verdicts remain distinct and require no self-referential SHA cycle. The model neither reinterprets accepted legacy contracts nor authorizes their retroactive editing.
